E um dos problemas mais traiçoeiros que existem é o tal do training serving skill. O nome é complicado, mas a ideia é simples. Pensa assim: o jeito que os dados são preparados e transformados durante o treinamento do modelo é diferente do jeito que isso acontece lá na produção no dia a dia. A primeira grande solução é um tipo de planta mestra de arquitetura proposta pelo Jindowen, que traz ordem, clareza e método pra construção de sistemas de IA. Essa é a arquitetura FTI. FTI de feature training e inference ou em bom português atributo, treinamento e inferência. A grande sacada aqui é a simplicidade e a clareza. A ideia é quebrar qualquer sistema de IA nesses três pipelines que são totalmente independentes. Cada um tem uma função muito clara e eles conversam entre si por uma camada de dados compartilhada. Isso muda tudo em termos de organização e colaboração. Certo? Vamos dar uma olhada nesse diagrama para entender melhor como funciona. Olha só, aqui à esquerda, o pipeline de feature pega os dados brutos e transforma em features, que são as características que um modelo vai usar. Essas features ficam guardadas no feature store. Aí no centro, o pipeline de training pega essas features e usa para treinar os modelos, que por sua vez são salvos no model. E por fim, à

[3:02]direita, o pipeline de Inference usa o modelo do registro e features novas para fazer as previsões no mundo real. É tudo modular, tudo conectado. Lindo, né? Então, para ficar bem claro, o primeiro pilar, o de feature, é quem cria a matéria-pra, os tijolos do sistema, de forma que possam ser reutilizados. O segundo pilar, o de training, usa esses tijolos para construir o cérebro da operação, que é o modelo. E o terceiro pilar, o de inference, coloca esse cérebro para trabalhar, para tomar decisões. Essa separação de papéis é o segredo para ter um sistema organizado e que consegue crescer. OK? Agora a gente já tem a planta da casa. A estrutura tá definida, mas e os materiais de construção? É criar uma taxonomia, uma classificação que define exatamente onde e quando cada tipo de transformação de dado pode acontecer. Isso acaba com a ambiguidade e força a consistência em todo o processo. Já as que dependem do modelo, as modelo no treinamento quanto na inferência para garantir a consistência. E as on são para aqueles dados que chegam em tempo real. Esse mapa é a receita para evitar discrepância. Então, para resumir, as transformações MIT, que são independentes, são feitas uma vez só lá no pipeline de feature e criam atributos que qualquer modelo pode usar. Será que é possível ter uma garantia ainda mais forte, quase matemática, de que o sistema não vai falhar? Isso nos leva ao nosso último e mais fascinante conceito. É aqui que entra a correção por construção ou CBC. Pensa nisso como o cálculo estrutural de um engenheiro civil antes de construir uma ponte. Em vez de só testar o sistema depois que ele já tá pronto e torcer pro melhor, a abordagem CBC garante que ele está correto desde o design, usando verificação formal, matemática mesmo, para provar que ele atende aos requisitos antes de uma única linha de código ser escrita. E a linguagem usada para fazer essas provas formais é a lógica temporal linear proposicional, a PLTL. Não precisa se assustar com o nome. Pensa nela como uma gramática super precisa que serve para descrever o

E como isso funciona? Na prática? O fluxo é mais ou menos assim. Primeiro a gente modela o comportamento do sistema, geralmente com diagramas. Depois esse modelo é traduzido automaticamente pra linguagem formal PLTL. Aí ferramentas matemáticas, os chamados provadores de teoremas, entram em ação para caçar qualquer falha ou contradição lógica. E só no final, quando tudo está matematicamente verificado, um esqueleto de código que já nasce correto é gerado a partir desse modelo. Quando a gente junta todas essas peças, fica muito claro. Estamos saindo da era do improviso, do artesanato e entrando de vez na era da engenharia de IA.
