02 — Realidade Atual

A dor que o modelo agentic resolve

Múltiplos times trabalham nas mesmas orgs Salesforce (QA, PreProd, Produção), cada um com seu repositório no GitHub. Sem disciplina, esse cenário federado vira uma guerra silenciosa de metadata. Esses são os sintomas:

⚠

Conflitos de metadata entre times

Dois times alteram o mesmo Account.object-meta.xml em sprints paralelas. O último deploy ganha — e silenciosamente sobrescreve campos do outro time.

team-billing · adiciona External_Tax_Id__c
team-crm · adiciona Customer_Tier__c
⚠ ambos editam Account em paralelo
⛓

Deploy quebra outro domínio

Uma trigger nova em Opportunity do time de Vendas faz a integração de Faturamento estourar em produção. Ninguém viu vir.

  • · Sem ownership por objeto
  • · Sem teste de contrato cruzado
  • · Sem aviso entre repositórios
⌕

Falta de rastreabilidade

“Quem mudou esse Flow?” vira arqueologia: change set sem PR, PR sem requisito, requisito sem dono. A auditoria sofre — a confiança também.

⇄

Dependência manual do Flosum

Promoções viram clique manual e tribal knowledge: “fala com o fulano que ele aprova”. O Flosum é a ferramenta certa, mas o uso é improvisado.

$

Desperdício de ACUs e tempo

Sem spec, o Devin entra em loop: reescreve, retesta, refaz. Cada iteração consome ACUs e devolve PRs com escopo errado.

⊘

Devin sem visão global

O agente opera por repositório. Ele não sabe que o time vizinho já criou aquela classe utilitária. A federação exige guardrails explícitos.

!
Insight central

O problema raiz não é “o Devin errou” — é contexto insuficiente e fronteiras frouxas. A solução não é mais código: é mais especificação, ownership e governança automatizada.

03 — Arquitetura

O novo modelo: federado e agentic

Não há repositório central. Cada time é dono do seu domínio, do seu repositório e da sua rastreabilidade. O Devin executa, o Flosum promove, o GitHub é a verdade. Salesforce é o ponto de integração.

GitHub

Source of Truth

Cada time mantém seu repositório com SDX/MDAPI, specs, playbooks e knowledge-base. Branches protegidas, PRs obrigatórios.

Devin

Executor (Cognition)

Lê a spec, segue o playbook, gera Apex/LWC, abre o PR. Web UI para tarefas exploratórias, Devin CLI para tarefas repetíveis.

Flosum

Promotion Control

Único canal oficial de promoção entre orgs. Branch → Flosum Branch → Deployment Set → QA → PreProd → Prod.

Salesforce Orgs

Integration Surface

QA, PreProd, Prod compartilhadas pelos times. É o lugar onde os domínios se encontram — e onde a governança paga seus juros.

Diagrama conceitual

Times federados → GitHub → Devin → PR → Flosum → Orgs

Princípio 01

Ownership explícito

Cada metadata tem um time dono declarado. Sem dono = sem deploy.

Princípio 02

Spec antes de código

Nada vai pro Devin sem spec aprovada. A spec é o contrato com o agente.

Princípio 03

Flosum único caminho

Não existe deploy direto via SFDX para QA+. Tudo passa por Flosum.

04 — SDD

Spec Driven Development

SDD é a prática de descrever o que deve mudar, onde muda, por que muda e como verificar — antes de qualquer linha de código.

Para times humanos, SDD reduz retrabalho. Para agentes, SDD é existencial: sem spec, o Devin alucina escopo, edita arquivos errados, gera classes redundantes e queima ACUs.

✓
A spec é o prompt definitivo

Estruturada, versionada, revisada. O Devin a referencia, não a interpreta.

✓
A spec é o critério de aceite

PR válido = todos os checks da spec atendidos. Nada mais, nada menos.

✓
A spec é o registro histórico

Daqui a um ano, é a spec que explica o porquê — não o git blame.

❌ Codar direto

“Devin, cria uma trigger pra atualizar Account quando Opportunity fechar.”

  • · Quais campos atualizar?
  • · E se já existir trigger?
  • · Bulk-safe? Qual handler pattern?
  • · Como testar? Cobertura mínima?
  • · Quem aprova? Qual repositório?

→ Resultado: 4 iterações, 18 ACUs, PR errado.

✅ Spec antes

“Devin, implemente a spec SPEC-CRM-204.md seguindo o playbook apex-trigger.md.”

  • · Escopo, campos e regras claros
  • · Handler pattern já decidido
  • · Casos de teste explicitados
  • · Critério de aceite definido
  • · Owner de metadata identificado

→ Resultado: 1 iteração, 5 ACUs, PR pronto pra review.

specs/SPEC-CRM-204-account-tier.md
Entrada do Devin 
# SPEC-CRM-204 · Account Tier Recalculation

## Contexto
Quando uma Opportunity fecha como "Closed Won", o tier do
Account deve ser recalculado com base na soma de Amount
das oportunidades fechadas nos últimos 12 meses.

## Owner
- Repositório: repo-crm
- Time: crm-platform
- Metadata: Account, Opportunity, AccountTierService.cls

## Regras
- Amount >= 1.000.000 → "Platinum"
- Amount >= 250.000  → "Gold"
- Amount >= 50.000   → "Silver"
- demais                  → "Standard"

## Implementação
- Trigger handler: OpportunityTriggerHandler.afterUpdate
- Service: AccountTierService.recalculate(Set<Id> accountIds)
- Bulk-safe (até 10.000 Opportunities por transação)
- Sem SOQL/DML em loop

## Testes
- AccountTierServiceTest · cobertura mínima 90%
- Cenários: bulk, sem oportunidades, oportunidade reaberta

## Critério de aceite
- [ ] PR aprovado por @crm-leads
- [ ] Todos os testes passam em scratch org
- [ ] Sem alterações em metadata fora de Account/Opportunity
- [ ] CHANGELOG.md atualizado

// Geração guiada por SPEC-CRM-204 · revisão @crm-leads
public with sharing class AccountTierService {

    public static void recalculate(Set<Id> accountIds) {
        if (accountIds == null || accountIds.isEmpty()) return;

        Map<Id, Decimal> totals = aggregateLast12Months(accountIds);
        List<Account> toUpdate = new List<Account>();

        for (Account a : [SELECT Id, Tier__c FROM Account WHERE Id IN :accountIds]) {
            String tier = tierFor(totals.get(a.Id));
            if (a.Tier__c != tier) {
                a.Tier__c = tier;
                toUpdate.add(a);
            }
        }
        if (!toUpdate.isEmpty()) update toUpdate;
    }
    // ... aggregateLast12Months / tierFor
}
05 — Operação

Como trabalhar com o Devin

O Devin não é um colega. É uma função pura: dado um repositório, uma spec e um playbook, ele gera um PR. Tudo o que estiver fora desse trio vira ruído, retrabalho e ACU desperdiçado.

⌬

Devin Web UI

Exploratório

Use para: descoberta de impacto, refactors guiados, sessões de pair com humano, tarefas com várias rodadas de feedback visual (LWC, debug interativo).

  • · Ideal quando o escopo ainda está sendo formado
  • · Permite ver o raciocínio do agente passo a passo
  • · Pode pausar e reorientar mid-task
▸_

Devin CLI

Repetível

Use para: tarefas com spec madura, fan-out de pequenas correções, scripts de manutenção, integração com pre-commit/CI.

# Disparo padrão a partir do branch local
devin task run \
  --repo crm-platform \
  --spec specs/SPEC-CRM-204.md \
  --playbook .devin/playbooks/apex-trigger.md \
  --branch feature/CRM-204-account-tier
5.1 · Boas práticas
①

Sempre comece pela spec

Sem spec aprovada, não dispare o agente. A spec é o pré-requisito, não opcional.

②

Use playbooks

Padrões repetíveis em .devin/playbooks/ evitam reinventar a roda a cada tarefa.

③

Mantenha contexto no repo

Knowledge-base, ADRs, CODEOWNERS — tudo que reduz perguntas do agente.

④

Evite prompts vagos

“Melhora isso aqui” → ❌. Use a spec ou referencie um playbook concreto.

⑤

Defina escopo de arquivos

Diga explicitamente o que pode tocar. Limite blast radius com --paths.

⑥

Rodar validações localmente

Devin deve rodar sfdx force:source:deploy --check-only antes do PR.

⑦

Itere por incremento

Tarefas pequenas e revisáveis. Um agente preso é mais caro que cinco agentes felizes.

⑧

Humano aprova, agente executa

PR sempre passa por revisor humano. O Devin propõe, o time decide.

5.2 · Anti-patterns
✕

Pedir código direto sem contexto

Prompts como “cria uma trigger no Account” forçam o Devin a alucinar regras de negócio.

prompt: "Devin, otimiza o Apex de Account."
✕

Não definir ownership

Sem CODEOWNERS e sem matriz de metadata, o Devin pisa em outro time sem saber.

risco: alteração em Opportunity.object-meta.xml sem aprovação do time-vendas.
✕

Ignorar validações de CI

Pular deploy --check-only, lint e testes só empurra o erro pro Flosum.

consequência: deploy validado falha em PreProd → rollback manual → ACUs desperdiçados.
✕

Mudanças grandes demais

Spec gigante = sessão longa = mais alucinação. Quebre em 2-3 specs revisáveis.

regra: PR alvo < 600 linhas e 1 domínio. Acima disso, refaça a spec.
💡
Tip

Trate cada sessão do Devin como uma função idempotente: mesma spec + mesmo playbook + mesmo repo = mesmo PR. Se isso não vale, o problema está no contexto — nunca no agente.

06 — Custo

Otimização de ACUs

Cada ACU é dinheiro real. ACUs altos quase nunca vêm da complexidade da feature — vêm da fricção: o agente busca arquivos que já existiam, faz suposições erradas, refaz testes, descobre regras pelo PR. Reduzir ACU = remover fricção.

Alavanca 01

Evite loops

Cada retry sem novo input é ACU jogado fora. Pare, ajuste a spec, redispare.

Alavanca 02

Contexto completo

Knowledge-base, exemplos, glossário e padrões cortam perguntas redundantes.

Alavanca 03

Use playbooks

Tarefas conhecidas (trigger, LWC, validation rule) = playbook pronto = zero exploração.

Alavanca 04

Divida tarefas

2 specs de 200 linhas custam menos que 1 spec de 600 linhas. E são revisáveis.

Alavanca 05

Evite reprocessamento

Cache scripts scripts/setup.sh rápidos. Não force npm install a cada run.

08 — Trust

Governança e segurança

Em modelo federado, governança não é overhead — é o que permite a velocidade. Sem ela, todo time acaba pisando no outro e ninguém acelera.

!
Warning

Devin não tem visão global entre repositórios. Toda fronteira de domínio precisa ser explicitada por artefatos (CODEOWNERS, ownership matrix, branch protection), não por cultura oral.

⊙

Metadata Ownership

Matriz versionada de quem é dono de cada objeto, layout, flow ou permission set. Aplicada via CODEOWNERS + ownership-matrix.yml.

# ownership-matrix.yml
objects:
  Account: crm-platform
  Opportunity: sales-cloud
  Invoice__c: billing
shared:
  Profile.Admin: platform-core
◈

Ambientes compartilhados

QA/PreProd/Prod são compartilhadas. Nunca rode sfdx force:source:deploy manual contra QA+. Use scratch orgs ou sandboxes dedicadas para o agente.

  • · Devin escreve em scratch org pessoal
  • · QA+ recebe SOMENTE via Flosum
  • · Janelas de deploy negociadas no calendário
⛔

Restrições do Devin

Hard limits por configuração — não confiança no agente.

  • · Sem acesso de escrita fora do repo
  • · Sem credenciais de QA+
  • · Sem permissão para fechar PR sozinho
  • · Sem alteração em main direta
  • · Bloqueio de paths via .devin/restricted-paths
✓

Aprovação humana

Toda promoção entre ambientes exige humano apertando o botão. O Devin propõe; o time aprova.

.devin/playbooks/ crítico

Receitas passo-a-passo para tarefas recorrentes. Cada playbook descreve como implementar um padrão (handler de trigger, LWC com Apex controller, etc.) — o Devin segue à risca, evitando criatividade desnecessária e ACUs altos.

Trigger típico: --playbook .devin/playbooks/apex-trigger.md
.devin/knowledge-base/ contexto

O “mundo” do time: glossário, ADRs, convenções de Apex, exemplos de chamadas a APIs externas. O Devin lê antes de codar — é o que evita ele inventar nomes, padrões ou regras de negócio.

scripts/ automação

Comandos canônicos do repositório. Quando o Devin precisa setup, validate ou preparar entrega ao Flosum, ele invoca esses scripts — sem improvisar comandos shell. 

# scripts/validate.sh
sfdx force:source:deploy --check-only \
  --sourcepath force-app \
  --testlevel RunLocalTests \
  --json
specs/ contrato

Cada feature/refator vive como um SPEC-*.md. É o input principal do Devin e o checklist do reviewer humano. Specs são versionadas e revisadas como código.

ownership-matrix.yml guardrail

A fonte de verdade sobre quem é dono de qual metadata. Casado com o check ci/owner-guard, impede que o Devin (ou qualquer humano) edite metadata fora da fronteira do time.

.devin/playbooks/apex-trigger.md
Playbook canônico 
# Playbook · Apex Trigger

## Objetivo
Criar/alterar trigger Apex seguindo o padrão Trigger Handler com bulk-safety.

## Estrutura obrigatória
- XxxTrigger.trigger          → 1 linha por evento, delega ao handler
- XxxTriggerHandler.cls       → orquestra contexto (before/after × insert/update/delete)
- XxxService.cls              → regra de negócio (testável isoladamente)
- XxxTriggerHandlerTest.cls   → cenários de bulk + edge cases

## Regras
- 1 trigger por SObject (consulte trigger existente antes)
- Sem SOQL/DML em loop
- Sem hardcode de Ids
- @TestVisible apenas em métodos privados auxiliares

## Comandos do agente
1. Verifique se já existe trigger para o SObject
2. Aplique o template em force-app/main/default/triggers
3. Rode scripts/validate.sh
4. Atualize CHANGELOG.md

11 — Daily Driver

Checklist do desenvolvedor

Quatro fases. Imprima, fixe na parede, cole no template de PR. Cumprir essa lista é o trabalho.

①

Antes de começar

Prep
  • ☐ Existe um SPEC-*.md aprovado?
  • ☐ A metadata afetada está dentro do meu time (ownership-matrix)?
  • ☐ Existe playbook para esse tipo de tarefa?
  • ☐ A spec referencia knowledge-base relevante?
  • ☐ Branch criada a partir de main atualizada?
  • ☐ Scratch org / sandbox pessoal pronta?
②

Durante o desenvolvimento

Build
  • ☐ Disparei o Devin com --spec e --playbook?
  • ☐ Limitei o blast radius com --paths?
  • ☐ Cada loop de retry traz novo input?
  • ☐ ACUs estão dentro do orçamento esperado?
  • ☐ O Devin atualizou o CHANGELOG e adicionou testes?
  • ☐ Validações locais passaram (scripts/validate.sh)?
③

Antes de abrir o PR

Review
  • ☐ Título do PR referencia o SPEC-*?
  • ☐ Diff < 600 linhas e foco em 1 domínio?
  • ☐ Cobertura Apex ≥ 90% nos arquivos novos?
  • ☐ Sem alterações fora do meu ownership?
  • ☐ Critérios de aceite da spec marcados?
  • ☐ Todos os checks de CI verdes?
  • ☐ CODEOWNERS notificados via assignee?
④

Antes da produção

Deploy
  • ☐ PR mergeado em main?
  • ☐ Sincronização com Flosum confirmada?
  • ☐ Smoke tests passaram em QA?
  • ☐ Aprovação de PreProd registrada?
  • ☐ CAB aprovou janela e plano de rollback?
  • ☐ Tag de release linkada ao Deployment Id?
  • ☐ Stakeholders notificados pós-deploy?

12 — Conclusão

Desenvolvimento orientado a agentes,
governado por specs.

O Devin acelera. O SDD direciona. O Flosum protege. O GitHub registra. Quando os quatro andam juntos, o time entrega mais com menos esforço — e dorme melhor.

Resultado 01

Menos esforço manual

Boilerplate, testes e setup de PR são automáticos. O humano cuida do que humano faz melhor: regra de negócio e julgamento.

Resultado 02

Mais previsibilidade

Spec aprovada → entrega previsível. Mesmas entradas geram mesmas saídas. Roadmap deixa de ser ficção.

Resultado 03

Mais qualidade

Cobertura mínima como gate. Owner-guard como contrato. Flosum como porteiro. Erro humano vira exceção, não regra.

Resultado 04

Rastreabilidade total

Demanda → Spec → PR → Deployment → Tag. Toda mudança em produção tem genealogia clara em segundos.

“O repositório é o cérebro do agente.
O time é a consciência que o guia.”
