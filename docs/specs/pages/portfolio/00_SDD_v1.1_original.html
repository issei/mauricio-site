Nota de escopo: este documento é a especificação, não o código. Ele define objetivo, arquitetura de informação, design system, contratos de dados, requisitos de SEO/IA e critérios de aceite necessários para que qualquer engenheiro (humano ou agente) implemente o index.html final de forma determinística e sem ambiguidade.

Regra de ouro desta versão (v1.1): todo o conteúdo textual de cv.json e star.json deve ser compilado/embutido diretamente no HTML estático no momento da geração do arquivo — nunca carregado, montado ou revelado via JavaScript em tempo de execução. Isso é requisito duro para três públicos simultâneos: (a) crawlers de SEO/ATS, (b) agentes de IA que fazem parsing do HTML puro, e (c) ferramentas de tradução do navegador (Google Translate, Microsoft Translator, Safari Translate), que só traduzem texto que já existe como nó de texto real no DOM no momento em que analisam a página. Ver seção 4.1 para as regras detalhadas e seção 12 para os critérios de aceite correspondentes.

1. Visão Geral e Conceito

O produto é uma Single Page Application em arquivo único, servida em mauricio.issei.com.br, com um conceito de "Dual-Faced Portfolio": o mesmo HTML precisa performar bem para dois consumidores com necessidades opostas:

  1. Humanos (recrutadores, gestores, tech leads) — precisam de uma leitura rápida, visualmente elegante, que comunique senioridade (+20 anos) e resultados de negócio em poucos segundos de scroll.
  2. Máquinas (crawlers de SEO, parsers de ATS, agentes de IA que fazem RAG sobre currículos) — precisam de HTML semântico, marcação ARIA e um bloco JSON-LD exaustivo, capaz de reconstruir 100% do currículo sem depender do CSS/JS.

Consequência arquitetural direta: todo componente visual "bonito" (cards colapsáveis, carrossel de depoimentos, pills de skills) deve ter, no DOM, o conteúdo completo já renderizado em texto/semântica — nada pode existir apenas dentro de um data-* JS ou ser injetado exclusivamente após interação do usuário. Colapsar visualmente ≠ remover do DOM/acessibilidade.

Dentro do escopo:

  • 1 página (index.html), 6 seções + header + footer, conforme seção 5.
  • Modo claro e escuro (dark mode), com persistência local (ex.: localStorage, respeitando restrições do ambiente de destino).

Fora do escopo (não implementar nesta entrega):

  • Backend, formulário de contato com envio de e-mail (o CTA de contato aponta para mailto: e redes sociais).
  • CMS ou geração dinâmica — o conteúdo é estático, compilado a partir dos JSONs no momento do build.
  • Internacionalização (i18n) — página apenas em pt-BR nesta versão.

4.1 Estratégia de Renderização — Zero dependência de JS para conteúdo

Esta seção substitui qualquer indicação anterior de "expandir/colapsar via JS" ou "carrossel via JS" para fins de carregamento de conteúdo. O objetivo é que a página funcione, com todo o texto visível e correto, mesmo com JavaScript completamente desabilitado no navegador — e que ferramentas de tradução automática do navegador consigam varrer e traduzir 100% do conteúdo já na primeira renderização.

Regras obrigatórias:

  1. Compilação em build-time, não fetch em runtime. Todo o conteúdo de cv.json e star.json (todas as 5 experiências, os 19 projetos STAR, as 26 certificações, os 6 depoimentos, as 6 categorias de cursos Alura) deve ser transcrito/injetado como texto literal dentro das tags HTML no momento em que o index.html é gerado. É proibido: fetch('cv.json'), fetch('star.json'), XMLHttpRequest, import() dinâmico de dados, ou qualquer template renderizado no cliente após o DOMContentLoaded.
  2. Elementos expansíveis usam HTML nativo, não JS. Os cards STAR (seção 9.3) e o agrupamento de trilhas Alura (seção 9.4.4) devem ser implementados com os elementos nativos <details> / <summary>, e não com <div> + onclick + classList.toggle. Vantagens diretas: (a) o navegador já cuida de aria-expanded/foco/teclado sem nenhum JS; (b) o conteúdo interno permanece um nó de texto real do DOM mesmo fechado, logo é indexável, traduzível e legível por parser de IA independentemente do estado visual; (c) funciona 100% com JS desabilitado. Customizar apenas a aparência do <summary> via CSS (remover marcador nativo, adicionar ícone de seta rotacionável via ::marker/::before).
  3. Nada de display:none/hidden para esconder texto que deveria estar acessível. Se algum bloco precisar iniciar oculto por design, usar <details> (regra 2) ou técnicas puramente visuais que não removem o nó da árvore de acessibilidade (ex.: max-height: 0; overflow: hidden em conjunto com o atributo open do <details>), nunca content: "..." via CSS para texto que faz parte do currículo.
  4. Depoimentos (seção 9.5): grid estático ou scroll-snap em CSS puro, sem JS de "próximo/anterior". Usar display: grid (masonry/2-3 colunas) como padrão, ou, se o efeito de carrossel for desejado visualmente, overflow-x: auto; scroll-snap-type: x mandatory — em ambos os casos os 6 depoimentos completos já estão todos no DOM, visíveis por scroll/leitura contínua, sem depender de clique em botão de navegação para existir.
  5. Dark mode com fallback 100% CSS. O tema padrão deve respeitar @media (prefers-color-scheme: dark) nativamente; o botão de toggle em JS é apenas uma sobreposição de conveniência (progressive enhancement) que troca uma classe/atributo — se o JS falhar ou estiver desabilitado, o tema ainda funciona corretamente a partir da preferência do sistema.
  6. Sem Shadow DOM e sem Web Components com conteúdo encapsulado. Ferramentas de tradução e crawlers frequentemente não atravessam shadow root; todo o conteúdo textual deve viver no light DOM.
  7. Frases não devem ser fragmentadas artificialmente em múltiplos elementos inline via JS (ex.: um <span> por palavra para animação). Isso quebra a tradução automática, que trabalha melhor com frases inteiras em um nó de texto contíguo. Animações de entrada (fade/slide), se usadas, devem ser aplicadas ao elemento-contêiner (ex.: o <article> ou <li> inteiro), nunca fatiando o texto.
  8. Teste de aceite direto: abrir o DevTools, desabilitar JavaScript, recarregar a página (Ctrl+Shift+R) e confirmar visualmente que todo o texto de todas as seções, incluindo o conteúdo "de dentro" de cada card STAR e de cada grupo de cursos Alura, está presente e legível — apenas o toggle manual de tema e eventuais efeitos de transição podem deixar de funcionar.

6.4 Dark mode

  • Base sempre funcional sem JS: o tema segue @media (prefers-color-scheme: dark) nativamente via CSS puro — isso já cobre 100% dos visitantes, com ou sem JavaScript habilitado.
  • Toggle no header (ícone sol/lua) é uma camada de conveniência opcional que sobrepõe a preferência do sistema, aplicando/removendo a classe dark na raiz (<html class="dark">, tailwind.config = { darkMode: 'class' }) e persistindo a escolha. Trata-se de puro comportamento visual — não afeta a disponibilidade de nenhum conteúdo textual, portanto não conflita com a regra de zero-JS-para-conteúdo da seção 4.1.
  • Estado padrão: seguir preferência do sistema operacional na primeira visita.

9.3 <section id="experience"> — Timeline + STAR Cards

Estrutura geral: um <article> por vínculo empregatício, ordem cronológica inversa, usando Experiencia (5 itens) como fonte.

Experiência atual (Rede, fev/2018–presente): este é o <article> mais rico. Além do cabeçalho padrão (cargo, período, local, descrição, competências-chave), renderizar a lista de 19 projetos de star.json/Projetos como cards expansíveis, agrupados por ano (decrescente: 2025 → 2018).

Contrato de dados do STAR Card:

interface STARCard {
  nome: string;        // Projetos[].Nome
  periodo: string;     // Projetos[].Periodo (ano)
  situacao: string;    // Projetos[].Situacao
  tarefas: string[];   // Projetos[].Tarefas
  acoes: string[];     // Projetos[].Acoes
  resultados: string[];// Projetos[].Resultados  → destacar métricas numéricas (regex: %, MM, k, D0, D2) com <MetricBadge>
  tecnologias: string[]; // Projetos[].Tecnologias → renderizadas como <Pill>
}

Comportamento de UI (sem JS, conforme seção 4.1): cada STAR Card é um elemento <details class="star-card">. O <summary> é a "fachada fechada" do card e contém nome + periodo + tecnologias (pills) + até 1 resultado-resumo em destaque — todo esse conteúdo já é um nó de texto real, visível e traduzível mesmo com o <details> fechado. O corpo do <details> (irmão do <summary>, dentro do mesmo elemento) contém Situação → Tarefas → Ações → Resultados, cada bloco com seu rótulo semântico (Situação, Tarefa, Ação, Resultado) em <h4>/<dt>, reforçando a semântica STAR também para IA. Não usar <button> + <div> + JS para este padrão — o navegador nativamente cuida de aria-expanded, foco e teclado. CSS pode customizar livremente a seta/ícone do <summary> e a transição de abertura, mas o texto interno nunca é inserido, removido ou buscado via JavaScript.

10. Acessibilidade (WCAG 2.1 AA)

  • Hierarquia de headings sem saltos (H1 único no hero → H2 por seção → H3 por card/artigo).
  • Todo botão de expandir/colapsar usa aria-expanded + aria-controls.
  • Todo link externo usa rel="noopener noreferrer" + texto acessível indicando destino (não apenas "clique aqui").
  • Contraste mínimo AA em ambos os temas (ver seção 6.1).
  • Carrossel de depoimentos deve ser navegável por teclado (tabindex, setas) e ter aria-live="polite" se autoplay existir (recomenda-se não usar autoplay, para não prejudicar leitura por screen readers).
  • Imagens (avatar) com alt descritivo.
  • Foco visível (focus-visible) customizado com a cor --accent-primary.
  • Compatibilidade com tradução automática do navegador: por decorrência direta das regras da seção 4.1 (conteúdo sempre em texto real, sem Shadow DOM, sem fragmentação de frases via JS, uso de <details> nativo), a página deve poder ser traduzida integralmente pelas ferramentas embutidas do Chrome, Edge e Safari sem que nenhum trecho fique "preso" atrás de um clique em JS — inclusive o conteúdo interno dos cards STAR e dos accordions de Alura, mesmo fechados.
